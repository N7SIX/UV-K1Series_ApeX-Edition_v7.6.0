### Critical Bug Fix — Repeater Tail Tone Elimination (RTTE) Power Amplifier Timing

**File:** `App/app/app.c:1064-1078`, `App/app/app.c:1820-1828`

**Severity:** HIGH — Repeater systems unable to detect tail tone

**Problem:** When RTTE was enabled and PTT was released, `APP_EndTransmission()` was called immediately, which disabled the Power Amplifier (PA) before the RTTE countdown period. This meant the CTCSS/DCS tail tone was generated by the BK4819 but NOT transmitted through the PA, making RTTE completely ineffective for repeater systems. The repeater would continue transmitting until its own timeout (typically 3-5 seconds) instead of stopping immediately upon receiving the tail tone.

**Root Cause:** The original logic called `APP_EndTransmission()` (which sends tail tone and disables PA) immediately on PTT release, then started the RTTE countdown with PA already OFF. The tail tone was generated during the countdown but could not be transmitted.

**Fix:**
- Modified `APP_HandleEndTransmission()` to delay calling `APP_EndTransmission()` when RTTE is enabled
- RTTE countdown now runs with PA still enabled (maintaining transmit carrier)
- `APP_EndTransmission()` (which sends tail tone and disables PA) is only called when countdown reaches zero

**Sequence After Fix:**
1. User releases PTT
2. RTTE countdown starts (100-1000ms configurable), PA remains ON
3. Countdown expires → `APP_EndTransmission()` sends CTCSS/DCS tail tone through active PA
4. PA disabled after tail tone transmission

**Impact:** Repeater tail tone is now properly transmitted through the PA during the RTTE delay period, allowing repeaters to detect the tone and stop transmission as intended. This fix aligns with standard ham radio repeater tail timing practices (100-1000ms configurable per repeater requirements).

**EEPROM/Calibration:** No impact. Uses existing `REPEATER_TAIL_TONE_ELIMINATION` setting (0-10, each unit = 100ms).

## CRITICAL Findings

### C1. DTMF Kill/Revive/Call Matching — Out-of-Bounds Read
**File:** `App/app/dtmf.c` — `DTMF_HandleRequest()` (lines ~269, 308, 332, 356, 378)  
**Severity:** CRITICAL  

`DTMF_HandleRequest()` computes `Offset = gDTMF_RX_index - strlen(String)` and then calls `CompareMessage(gDTMF_RX + Offset, ...)`. `gDTMF_RX_index` is capped at `sizeof(gDTMF_RX)-1 = 16`, but `String` is built from EEPROM fields (`ANI_DTMF_ID`, `DTMF_SEPARATE_CODE`, `KILL_CODE`/`REVIVE_CODE`) whose lengths are not validated at load time. If `strlen(String) > gDTMF_RX_index`, `Offset` underflows (unsigned arithmetic), and `gDTMF_RX + Offset` reads far before the buffer — a genuine out-of-bounds read from arbitrary EEPROM contents.

**Impact:** Memory corruption read, potential crash, or security bypass of kill/revive codes.

**Fix (logic-preserving):** Clamp `Offset` before use:
```c
if (strlen(String) > gDTMF_RX_index)
    return;  // string too long to match
Offset = gDTMF_RX_index - strlen(String);
```
Also validate EEPROM code string lengths at load time in `SETTINGS_InitEEPROM()`.

### C2. REGA Transmit Blocks the Cooperative Kernel for Seconds
**File:** `App/app/rega.c:108-187` — `REGA_TransmitZvei()`  
**Severity:** CRITICAL  

`REGA_TransmitZvei()` performs the entire alarm/test as a blocking sequence: LED flashes with `SYSTEM_DelayMs(70/50/70)`, then `SYSTEM_DelayMs(1000)` for the tone itself. During this time, the cooperative scheduler cannot run `APP_Update()`, `APP_TimeSlice10ms()`, or `APP_TimeSlice500ms()`. This means:
- No key scanning (user cannot cancel)
- No battery monitoring
- No backlight timeout
- No DTMF decode
- No squelch processing

**Impact:** Radio becomes unresponsive for 1+ seconds during REGA alarm. User cannot cancel mid-transmit.

**Fix (logic-preserving):** Convert to a state machine driven by the 10ms timeslice, or at minimum add a key-check loop inside the blocking delay:
```c
// Inside the long delay, poll for EXIT key:
for (uint16_t i = 0; i < 100; i++) {
    SYSTEM_DelayMs(10);
    if (KEYBOARD_GetKey() == KEY_EXIT) break;
}
```

### C3. Unbounded Blocking Interrupt-Drain Loop in RADIO_SetupRegisters
**File:** `App/radio.c:798-806`  
**Severity:** CRITICAL  

```c
while (1)
{
    const uint16_t Status = BK4819_ReadRegister(BK4819_REG_0C);
    if ((Status & 1u) == 0) // INTERRUPT REQUEST
        break;
    BK4819_WriteRegister(BK4819_REG_02, 0);
    SYSTEM_DelayMs(1);
}
```

This is a **blocking, unbounded spin** in the single most-called hot path. `RADIO_SetupRegisters()` runs on every VFO switch, dual-watch toggle, end-of-RX, alarm off, and VFO reconfigure. If the BK4819 keeps asserting interrupts (e.g., squelch toggling, DTMF, CSS tail during active RX), this loop can spin for many milliseconds — each iteration is a bit-banged SPI read + write + a 1 ms `SYSTEM_DelayMs`. This directly adds to PTT-to-RF and VFO-switch latency.

**Impact:** Adds unpredictable latency to VFO switching and PTT response. In worst case, can stall the radio for tens of milliseconds.

**Fix (logic-preserving):** Bound the loop:
```c
for (uint8_t retry = 0; retry < 10; retry++)
{
    const uint16_t Status = BK4819_ReadRegister(BK4819_REG_0C);
    if ((Status & 1u) == 0)
        break;
    BK4819_WriteRegister(BK4819_REG_02, 0);
    SYSTEM_DelayMs(1);
}
```

### C4. EEPROM/Calibration Corruption Bugs (3 bugs, 2 power-loss windows)
**Files:** `App/settings.c`, `App/init.c`, `App/driver/eeprom.c`  
**Severity:** CRITICAL  

From the settings/EEPROM/boot audit:

1. **RSSI calib block / S0-S9 levels data collision:** The RSSI calibration block and S0/S9 level settings share overlapping EEPROM address space, causing calibration bytes to be corrupted when S0/S9 levels are saved.

2. **Boot-time forced attribute writeback destroys scan-exclusion bits:** Every boot, the firmware writes channel attributes back to EEPROM, which resets scan-exclusion bits that the user set. This happens on normal operation without any power fault.

3. **Power-loss windows in SETTINGS_Save:** The save path writes the full `gEeprom` struct in multiple EEPROM page writes. A power loss between writes leaves a partially-written, inconsistent EEPROM state with no rollback/recovery mechanism.

**Impact:** User data loss (scan exclusion reset every boot), calibration corruption (RSSI accuracy degrades), settings corruption on power loss.

**Fix (logic-preserving):** 
- Separate the RSSI calib and S0/S9 EEPROM addresses (verify no overlap)
- Skip the boot-time attribute writeback if attributes haven't changed
- Add a CRC/checksum to the settings block and implement atomic write (write to shadow, verify, then commit)

### H1. ST7565_FillScreen — Value Used as Both Loop Count and Fill Byte
**File:** `App/driver/st7565.c:204-212`  
**Severity:** HIGH  


`DrawLine()` uses `size_defVal` as both the loop count AND the fill byte when `lineBuffer` is NULL:

### H3. UI_PrintStringSmallNormalInverse — Potential Buffer Underflow
**File:** `App/ui/helper.c:121-147`  
**Severity:** HIGH  

```c
void UI_PrintStringSmallNormalInverse(const char *pString, uint8_t Start, uint8_t End, uint8_t Line)
{
    UI_PrintStringSmallNormal(pString, Start, End, Line);
    uint8_t len = strlen(pString);
    uint8_t char_width = 7; // small font is typically 6px wide

    uint8_t x_start = Start;
    uint8_t x_end   = Start + (len * char_width) + 1;

    if (End != 0 && x_end > End)
        x_end = End;

    gFrameBuffer[Line][x_start - 1] ^= 0x7F;  // <-- underflow if x_start == 0
    for (uint8_t x = x_start; x < x_end; x++)
    {
        gFrameBuffer[Line][x] ^= 0xFF;
        gFrameBuffer[Line - 1][x] ^= 0x80;     // <-- underflow if Line == 0
    }
    gFrameBuffer[Line][x_end + 0] ^= 0x7F;     // <-- overflow if x_end == 127
}
```

Three issues:
1. If `Start == 0`, `x_start - 1` underflows to 255, writing to `gFrameBuffer[Line][255]` — out of bounds.
2. If `Line == 0`, `Line - 1` underflows to 255 — out of bounds.
3. If `x_end == 127`, `x_end + 0` is fine but the pattern is fragile.
4. `char_width = 7` is wrong — the small font is 6px wide (see `gFontSmall` definition). The comment even says "typically 6px wide" but uses 7.

This function is called from `UI_DisplayMain()` for channel number and frequency band display (lines 1585, 1611), so `Start` is typically 1-2 and `Line` is 1-5, avoiding the underflow in practice. But it's a latent bug.

**Fix:** Add bounds checks:
```c
if (x_start > 0)
    gFrameBuffer[Line][x_start - 1] ^= 0x7F;
if (Line > 0) {
    for (uint8_t x = x_start; x < x_end; x++)
        gFrameBuffer[Line - 1][x] ^= 0x80;
}
```
Also fix `char_width` to match the actual font width.

### H6. K5Viewer Packet Send — Blocking UART in Real-Time Loops
**File:** `App/app/app.c:1650-1680`  
**Severity:** HIGH (partially mitigated by v7.6.9B rate limiting)  

`RXTX_LOG_SendK5ViewerPacket()` scans up to 1024 flash entries and sends 1629 bytes over UART at 38400 baud (~424ms blocking). The v7.6.9B fix rate-limits this to 1 update per second, but the underlying call is still blocking when it does fire. During that ~424ms, no key scanning, no squelch, no battery monitoring occurs.

**Impact:** Momentary stutter once per second during active K5Viewer connection.

**Fix (logic-preserving):** Split the packet into chunks sent across multiple 10ms timeslices, or use DMA/interrupt-driven UART TX.

### H7. Scanner Dwell Time Inconsistency
**File:** `App/app/scanner.c`, `App/app/chFrScanner.c`  
**Severity:** HIGH  

The scanner dwell time uses different timing paths for MR channel scan vs. frequency range scan, and the sub-audible scan detection adds additional delay that isn't accounted for in the dwell timer. This can cause:
- Missed signals on fast-scanning channels
- Inconsistent dwell times between MR and VFO scan modes
- Sub-audible scan detection to timeout before the tone is fully decoded

**Fix (logic-preserving):** Unify the dwell timer to account for sub-audible detection time, and ensure both scan modes use the same base dwell.

### H8. Waterfall Persistence Math — Integer Division Precision Loss
**File:** `App/app/waterfall.c`  
**Severity:** HIGH  

The waterfall persistence decay uses integer arithmetic that loses precision at low signal levels. The decay formula `(value * decay_factor) / 100` can produce 0 for small values, causing the waterfall to show gaps at low signal levels. The peak hold logic also has a rounding issue where `peakIndex` can be stale if the signal drops suddenly.

**Fix (logic-preserving):** Use a fixed-point representation with more bits of precision, or add a minimum threshold below which the decay is skipped.

### M3. SPI_WriteByte — No Timeout on Busy-Wait
**File:** `App/driver/st7565.c:98-109`  
**Severity:** MEDIUM  


### M8. BK4819 Bit-Banged SPI — 1µs Per Bit, No CS Timeout
**File:** `App/driver/bk4819.c:167-187`

The BK4819 uses bit-banged 3-wire SPI with `SYSTICK_DelayUs(1)` per clock edge. A 24-bit register access takes ~48µs. There's no timeout on the CS assert — if the BK4819 doesn't respond, the read returns garbage but the system continues. Register writes have no readback verification.
